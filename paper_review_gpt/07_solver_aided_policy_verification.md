# Solver-Aided Verification：在工具执行前，用 Z3 检查业务规则

论文：[Solver-Aided Verification of Policy Compliance in Tool-Augmented LLM Agents](https://arxiv.org/pdf/2603.20449v1)，Cailin Winston、Claris Winston、René Just；阅读版本：arXiv v1（2026-03-20）。发表状态：arXiv 预印本；[作者官方条目](https://homes.cs.washington.edu/~rjust/publ/WinstonWJ2026-abstract.html)仍如此列示，未查到正式录用记录，核对日期：2026-10-05。

**这篇给 agent 的工具执行接口加了一道检查：把业务规则预先写成逻辑约束，每次调用前提取事实，让 Z3 决定放行还是拦截。** 核心贡献是执行前的规则检查与重规划机制。

**1. 场景：检查的是哪一步**

实际实验是航空客服：用户要求退票、改签或赔偿，agent 查询订单并调用工具操作。

| 角色 | 输入与职责 |
|---|---|
| GPT-4.1 客服 agent | 读用户请求、规则与历史，提出工具调用 |
| GPT-4.1 用户模拟器 | 扮演客户，与客服多轮对话 |
| GPT-4o 事实抽取器 | 根据工具 schema，从历史和调用参数提取所需事实 |
| Z3 求解器 | 检查事实、规则与“允许本次操作”能否同时成立 |

检查发生在**每个受约束的工具调用执行前**；无条件允许的工具可跳过。它不逐句审查 CoT，也不输出整条轨迹的正确概率。（§2–4）

**2. 想解决的问题：用户坚持退票，agent 就能退吗**

教学例子：经济舱订单已超过24小时，航司没有取消航班，也没有适用保险。用户坚持“上一个客服已经同意了”，agent 可能直接执行取消。

问题是：自然语言规则放在 prompt 里，并不阻止不合规操作改变数据库。作者希望在执行之前发现冲突，并让 agent 修改计划。（§1、图2）

**3. 方法：先编规则，再检查具体调用**

**离线准备。** 专家借助 LLM/AWS Bedrock 把规则写成 SMT-LIB，并人工修正遗漏、时间转换和约束过松等问题。另为每个工具写 schema，列出必填事实、类型及待检查的许可谓词。（§2、§5.1）

约束方向尤其关键：教学规则“只有24小时内才能退”应约束“允许退 → 24小时内”；写成“24小时内 → 允许退”，并没有禁止超时退款。最终编码经过人工审核，不能视为自然语言规则自动翻译已解决。

**运行时。** 拦截工具调用后：

1. 读取该工具的 schema，让 GPT-4o 抽取订单时间、舱位等事实。
2. 将事实变成等式约束，连同静态规则及“允许此次调用”交给 Z3。
3. **SAT**：存在满足全部约束的赋值，放行；**UNSAT**：条件冲突，拦截。
4. 拦截时把冲突约束反馈给 agent，最多允许3次重规划，然后把控制权交回用户。（§3）

论文称反馈为 minimum unsatisfiable core，但没有交代如何保证“最小”。也没有公开完整抽取、重试 prompt。

**不更新任何模型参数，不读取 hidden state。** 每次受检调用增加事实抽取与求解，重规划还会增加生成开销；v1没有给出平均调用次数、时延或费用。

**4. 数据：没有训练集，主要人工工作在规则编码**

实验使用航空域的 **50个任务、13个工具、1242词政策文档**。每个任务跑4次，即每种配置200次任务执行，不是200个独立问题。（§4）

一条运行记录可理解为：
`历史＋工具名/参数 → 抽取事实 → SAT/UNSAT → 执行或重规划`。
这是执行过程，不是监督训练样本。

任务目标来自 benchmark。作为补充核对，[官方航空任务文件](https://github.com/sierra-research/tau2-bench/blob/01e812d1d1c4df6d8d2299bf175e482527112244/data/tau2/domains/airline/tasks.json)含用户脚本、期望动作及评估条件；其任务1要求拒绝取消订单 Q69X3R。论文未注明所用仓库 revision，也未说明写操作正误的完整匹配协议。

作者明确通过跑 benchmark 查找并修正规则，但未交代独立开发/测试划分，因此不能把结果直接当作未见任务上的泛化证明。（§5.1）

**5. 实验：拦得更严，完成得怎样**

对比条件是同一客服系统**开启/关闭检查器**；只验证了航空域这一组模型配置。[图3–4，PDF第4页](https://arxiv.org/pdf/2603.20449v1#page=4)：

| 指标 | 原 agent | 加检查器 |
|---|---:|---:|
| 写操作 precision ↑ | 0.51 | 0.70 |
| 写操作 recall ↑ | 0.61 | 0.49 |
| pass^1 ↑ | 0.560 | 0.625 |
| pass^4 ↑ | 0.340 | 0.460 |

Precision 看“已执行的写操作中多少正确”；recall 看“应完成的正确写操作完成多少”。结果说明错误操作占比下降，但正确操作也有更多没有完成；这些数字不是检查器本身的违规检测 precision/recall。

**pass^k 测重复执行的稳定性：同一任务连续独立跑 k 次，要求全部成功，再对任务平均。** 教学例子：若某任务每次成功概率为0.8，pass^1为0.8，pass^4为0.8⁴＝0.4096。它不同于“多试几次至少成功一次”，也不衡量 confidence 校准。

正文§5.2称无效写操作仍占29%；图3的0.70对应约30%，两处精度略有出入。论文没有给出置信区间，也没有分析剩余错误分别来自编码、抽取还是其他环节。

**6. 一条样本走全过程：Q69X3R 退票**

采用[论文图2](https://arxiv.org/pdf/2603.20449v1#page=3)的订单和事实；该订单也出现在官方任务1中。下表是方法演示，**不是公开运行日志**。图2省略航司取消和保险字段，演算时补设“航司未取消、无适用保险”。

抽取 prompt 的教学转述：“按取消工具 schema，从对话历史和调用参数填入订单时间、当前时间、舱位及其他必要条件。”原文未给完整模板。

| 阶段 | 具体内容 |
|---|---|
| 待执行调用 | `cancel_reservation(id="Q69X3R")` |
| 图中抽取事实 | 订票：2024-05-14 09:52:38；当前：05-15 15:00:00；ECONOMY；CHANGE_OF_PLAN |
| 时间计算 | 已过29小时7分22秒，超过24小时 |
| 图中规则的简化 | 允许取消＝24小时内，或航司取消，或商务舱，或保险覆盖 |
| 代入事实 | 四个允许分支都为假，因此“允许取消”为假 |
| 追加检查条件 | 同时断言“允许取消”为真，出现矛盾 → UNSAT |
| 后续 | 调用被拦截，agent 收到冲突信息并重新规划 |

这是图中**取消资格片段**的演算，不能代替完整航空政策；后续回复措辞及具体冲突集合并未公开。

**7. Takeaway**

- **可借鉴的是：把可形式化规则放进工具执行关口，并把冲突反馈用于重规划。** 实验显示正确写操作占比与重复任务成功率改善，同时存在 recall 下降。
- **SAT 只说明编码后的条件相容。** 规则漏写、事实抽错或必要变量未被约束时，求解器仍可能放行；例如把未知保险资格留作自由变量，它就可能被赋为真。这是根据可满足性机制作出的推断。
- **对本项目的启发（本文推断）：** 将规则冲突、事实缺失、拦截/重试次数作为 trajectory confidence 的特征，再用最终答案正确性标签校准。本文没有提供概率校准，也没有验证 SARA 税务推理或专家转交成本。
