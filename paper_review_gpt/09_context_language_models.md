# Context Language Models：让 agent 直接编辑下一轮会读到的上下文

论文：[Context Language Models](https://arxiv.org/pdf/2609.37725v1)，Rulin Shao 等；阅读版本：arXiv v1（2026-09-29）。发表状态：arXiv 预印本；核对 [arXiv 条目](https://arxiv.org/abs/2609.37725v1)、[作者主页](https://rulinshao.github.io/)及[官方仓库](https://github.com/facebookresearch/context-language-models)，未查到公开正式录用记录，核对日期：2026-10-06。

**把 agent 的工作上下文映射成可编辑文件，让它自己决定删什么、留什么、怎样整理，再将修改结果作为下一轮输入。** 现有模型即可使用；作者另做了文字 skill 优化、RL 训练和缓存优化。

**1. 场景：长任务中的“工作记忆”**

Agent 连续检索、运行代码或优化仓库，累积大量工具输出和中间尝试。输入是任务与当前历史，输出仍是答案、代码或下一步操作；CLM 增加了“改写后续输入”的能力。

实际测试包括深度检索、终端编程、最长12小时的单仓库优化，以及超过24小时的多仓库协作。模型继续按通常的 next-token 方式生成；“原生管理上下文”在这里指模型通过代码选择上下文操作。（§4–5）

**2. 想解决的问题：总结容易丢信息，保留全部又会塞满**

教学失败例子：维护一张16×16数独表，用户只要求把左上角改成9。模型重写整张表时误改另一格；如果每轮追加一份完整棋盘，历史又越来越长。

常见 harness 到阈值后统一总结；CLM 允许模型直接修改所需字段、删除过期内容，或把材料存到外部文件后只留索引。**仅把材料另存为文件，不会自动让已读入的材料退出上下文。**（§3–4）

**3. 方法：文件如何变成下一轮输入**

1. Harness 把可编辑历史写入文本文件，各条消息带角色和轮次标记，并告诉模型文件路径。
2. 模型生成 Bash/Python 等代码，执行删除、替换、摘要或外存操作；不编辑时照常追加历史。
3. Harness 读回文件，解析成消息列表，再调用同一个模型。因此编辑影响的是下一轮实际输入。（§4.1）

[公开 Harbor 实现](https://github.com/facebookresearch/context-language-models/blob/18dc11115f50f261233c5bba7937834491e307e8/clm/clm_harness/README.md)使用 `/tmp/.live_ctx/LIVE_CTX_MAIN.txt`，**固定保留 system prompt 和原始任务**，并有预算提醒、超限回退和编辑检查。因此仍需 harness 执行同步与约束。多 agent 时可各有一份上下文文件。

作者另提供两种学习方式（§4.2）：

- **文字 skill 优化：** 固定模型参数，让 proposer 读训练轨迹、改写管理说明，在开发集选择准确且省计算的版本，最后测留出集。
- **RL：** 更新 Qwen3.5-9B。每题采样多条完整轨迹，按最终答对与否计算 GRPO advantage；保存每次调用当时的上下文，分别计算该次输出的 loss，避免用已被改写的最终历史回算早期动作。

效率信号只在成功轨迹之间比较：教学例子中，两条成功轨迹分别耗6、10 PFLOPs，均值8，对应效率 advantage 为 +0.25、−0.25；失败轨迹为0，成功不足两条时全部为0。实现以0.25权重把它加到**上下文编辑 token**，任务 outcome advantage 仍覆盖生成片段。（§4.2、附录E；[RL 实现说明](https://github.com/facebookresearch/context-language-models/blob/18dc11115f50f261233c5bba7937834491e307e8/clm/clm_rl/README.md)）

另有可选的 **Suffix Cache Reuse（SCR）**：把 `A+B+C` 改成 `A+B′+C` 后，普通前缀缓存需重算 `B′+C`；SCR 还复用 C 的旧状态，只计算新增部分。C 的状态仍包含旧前文影响，故这是近似复用，不能保证等价于完整重算；需要修改推理服务器。（§4.3、附录B）

**4. 训练数据：哪些更新参数，哪些只选说明文字**

| 用途 | 数据与监督 |
|---|---|
| 零样本 CLM | 不涉及参数训练，给现有模型文件编辑能力 |
| 文字 skill 优化 | ContextBench 合成任务；每候选先测6条训练实例，通过后再测12条；每任务102条开发实例；辅助优化的最终测试为102条×3个种子，使用程序评分 |
| RL | OpenResearcher 的3,040条深度检索题；每步8题×32条在线轨迹，训练70步；GPT-5.4-nano 按 DeepSearchQA rubric 给0/1任务奖励 |
| RL 选模型/测试 | 500条留出的 OpenResearcher 题选 checkpoint，再测830条 BrowseComp-Plus 题 |

一条 RL 记录可理解为：`检索题 → [(当时上下文, 生成的操作/回答), …] → 最终答案判分＋整条轨迹 FLOPs`。监督来自最终结果和计算量，没有逐步“正确编辑”的人工标签；3,040是问题数，不是轨迹数。（附录E）

**5. 实验：准确率和计算量要一起看**

ContextBench 测原样保留信息、更新棋盘、存取键值和查询日志，采用确定性答案检查；“数独”考的是按指令维护状态。BrowseComp-Plus 在固定文档库检索后回答，用模型 judge 判答案；终端编程由任务 verifier 判分。（§3、附录D–E）

零样本比较包含定时摘要、Self-Compact、ACM、MEM1 和 RLM。Qwen3.6-27B 的 CLM 在 BrowseComp-Plus 得59.4%，比最强的摘要基线**相对提高11.4%**，FLOPs 少21.5%；TBLite 从摘要基线67.0%升到73.7%，FLOPs 少9%。（§5.1.1）

RL 的同一组结果如下，箭头表示训练前→后（表2）：

| Qwen3.5-9B 系统 | 准确率 ↑ | PFLOPs/题 ↓ |
|---|---:|---:|
| Summary harness | 34.7% → 42.1% | 4.01 → 2.19 |
| CLM | 28.8% → 42.5% | 1.52 → 1.34 |

**训练后准确率接近，CLM 计算量低约38.8%。** 在这组设置下，训练前 CLM 准确率反而更低。文字 skill 优化另将 KV Store 留出测试准确率从38.3%升到74.2%；SCR 则在独立服务实验中再减少35%计算量，不能把这些数字合并为一个实验。（§5.2–5.3、附录F）

这里的主要成本指标是计入前缀缓存失效与重新 prefill（读取上下文）的推理 FLOPs，1 PFLOP 为10¹⁵次浮点运算，**不直接等于时延、账单或训练成本**。例如提前改一小段可能迫使很长的后文重算，字符更少也未必更省。

复现注意：v1 正文将检索实验预算写为32K，附录E写23,560；RL 与零样本段使用的 judge 也不同。表2与附录图17的9B初始结果不可混用。CLM 编辑轮次不计入任务步数，但计入计算量，固定步数不等于固定模型调用次数。附录E中两个 RL 系统的奖励和轮次配置也不同，表2不能单独隔离文件编辑的贡献。

**6. 一条样本走全过程：只更新数独的一格**

使用[图16（PDF第20页）](https://arxiv.org/pdf/2609.37725v1#page=20)的真实输入与期望输出。下面编辑过程是教学演示，并非公开运行日志；棋盘只展示相关字段。

| 阶段 | 具体内容 |
|---|---|
| 初始状态 | `VERSION: 0`；`(1,1,.) (1,2,8) …` |
| 用户指令的简化转述 | 把第1行第1列设为9，版本加1，其他格不变 |
| 模型生成操作 | 定位上下文文件中的当前棋盘块，只替换版本号及 `(1,1,.)` |
| 执行后内容 | `VERSION: 1`；`(1,1,9) (1,2,8) …`，其余255格保持原值 |
| 下一轮模型输入 | Harness 读回修改后的消息，模型看到更新后的棋盘 |
| 如何判分 | 检查上下文中的棋盘版本与全部格子是否准确；答案仅在普通外部文件中不计分 |

这条样本无需训练；标签由已知棋盘和更新指令确定。它说明“文件编辑→真实上下文更新”的连接，也说明这项测试衡量状态管理能力。（附录D、表3）

**7. Takeaway**

- 可借鉴的是把上下文管理变成 agent 可编程的动作，再用任务成功与计算成本优化。RLM 主要控制怎样读取外部长输入，CLM 控制读入之后及交互中累积的历史。（§2、附录A）
- 收益依赖模型能力与设置；SCR 保留旧缓存影响，预算和解析仍需 harness。当前官方 README 还将 ContextBench 列为待发布，RL 目录只提供改动说明和补丁，完整训练依赖外部框架。
- **对本项目的启发（本文推断）：** 若用可编辑上下文减少 DAR 的重复日志，应另存完整、不可被 agent 改写的执行记录供 verifier 使用，避免检查器只看到 agent 自己筛选的证据。本论文没有验证 confidence 校准或 SARA 上的效果。
